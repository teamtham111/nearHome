# Fair-price buyer interface

Updated 2026-08-05.

The normal comparison screen intentionally translates valuation evidence into
buyer-facing conclusions. Technical diagnostics remain available to developers
through the API, logs and tests, but are intentionally omitted from the normal
buyer-facing interface because they do not directly help a buyer interpret the
valuation.

## What produces each displayed value

The runtime roles are separate:

| Display concern | Runtime source |
| --- | --- |
| Central estimate | Prebuilt CatBoost artifact (`catboost_v2_artifact`), validated against the bundled transaction snapshot |
| Likely range | Asymmetric residual interval saved with the prebuilt artifact |
| Comparable transactions | Weighted-comparable selector (`weighted_comparables_v3`), used as market evidence and as the explicit fallback when CatBoost cannot produce a prediction |
| Confidence | Comparable-selection evidence: effective weighted count, similarity, recency, spread, missing optional fields and filter relaxation; when no comparable selection exists, the CatBoost calibration-row availability is used as a fallback signal |
| Remaining lease | Separate canonical lease estimator, using official exact evidence, exact-block transaction expiry evidence, HDB commencement-year evidence, then low-confidence listing-stated evidence |

CatBoost does not calculate the remaining lease. Weighted comparables do not
generate the central estimate when CatBoost succeeds; they explain the local
market evidence and provide the documented fallback.

## Buyer-facing translation

The reusable translation helpers live in
`apps/web/src/lib/fair-price.ts` and are rendered by
`apps/web/src/components/comparison-view.tsx`.

The asking-price difference is consistently described from the asking-price
perspective:

```text
difference = asking_price - central_estimate
percentage = difference / central_estimate * 100
```

The UI displays the absolute amount and direction, for example `S$11,748
above estimate · 1.4%`. Equal values display `Matches estimate`; missing or
invalid asking prices or estimates display `Asking price unavailable`. The
legacy API `value_gap_percentage` remains available for compatibility but is
not rendered because its inverse perspective was easy to misread.

Price-assessment labels use these initial product-interpretation bands:

| Absolute difference | Buyer-facing label |
| ---: | --- |
| ≤ 2% | Close to estimated market value |
| > 2% to 5% | Slightly above/below estimate |
| > 5% to 10% | Above/below estimate |
| > 10% | Significantly above/below estimate |

These are interpretation bands, not model-confidence thresholds. They may be
recalibrated later using historical prediction error.

## Evidence presentation

Each listing starts as a compact disclosure summary showing the estimated value,
likely range, asking-price comparison, assessment and confidence. Expanding it
shows:

- a concise explanation of the estimate and confidence;
- the applied, omitted and relaxed comparison criteria in prose;
- property information, including the separate lease evidence and readable source label;
- up to ten strongest recent comparable transactions by default, with the
  total eligible transaction count;
- a buyer-facing explanation that these rows are contextual evidence, not the
  complete eligible collection and not a ten-row average;
- broad relevance labels and an expandable reason based only on confirmed fields;
- limitations supported by the actual response evidence.

The interface does not render raw JSON, model/version identifiers, calibration
counts, candidate-stage counts, relaxation levels, raw filter-status objects,
internal source identifiers or decimal similarity values.

## Comparable relevance labels

The comparable selector multiplies its recency, area, lease, location and
optional model/storey components, producing a score in the observed 0–1 range.
An inspection of 78,138 selected comparable rows from a 200-listing sample
produced a median similarity of 0.0769, a 75th percentile of 0.1350 and a 90th
percentile of 0.2171. The UI therefore uses broad labels rather than false
precision:

| Similarity | Label |
| ---: | --- |
| ≥ 0.20 | Very similar |
| ≥ 0.10 and < 0.20 | Similar |
| ≥ 0.05 and < 0.10 | Moderately similar |
| < 0.05 or unavailable | Contextual match |

These labels describe evidence relevance only. They are not probability or
confidence claims. The normal API returns at most ten displayed rows, ordered
by the canonical similarity score, then recency, then transaction ID. Duplicate
canonical transaction IDs are removed before eligibility counts and weighting.
The complete eligible collection remains available to the valuation engine and
backend audit/debug data but is not sent to the normal browser response.

The estimate is generated by the active valuation model from historical HDB
resale patterns. The displayed transactions are contextual examples and must
not be described as the transactions used alone to calculate the estimate.

## Developer diagnostics retained

The API continues to retain technical fields needed for auditability and
debugging, including model metadata, training/calibration rows, candidate
counts, effective weighted count, similarity, filter status, relaxation steps,
stage counts and source identifiers. They are documented in
[fair-price-audit.md](./fair-price-audit.md) and
[model-card.md](./model-card.md), but are not part of the standard buyer UI.
